# H2Classic 1.5 (title update 5) - work notes (started 18 Nov 2026, after build 37 was confirmed by the user)
Goal: a second exe that runs the 1.5 XBE (h2classic\T\$u\default.xbe = u5 English, CRC32 a5b0b715, 4,919,296 bytes,
cert version 0x803) the way H2Classic runs 1.0: unchanged functions as compiled source (the 1.0 decomp's), changed
ones as 1.5's own code (routed), data in place at 1.5's addresses, every layer patch at its 1.5 address. First
milestone: "1.5" at the bottom right of the Press Start screen. Then: the launcher's version choice, XFindFirstContent
/ content signatures so the packs (h2classic\T\$c) show up, DLC maps loading.
Facts: same XDK 5849 libraries; .text +0xa0e0; library sections shifted by exactly +0xa0e0 (DSOUND 0x379c60->0x383d40,
XONLINE, XNET, BINK*); fmap.py: 14,974 / 15,793 functions the same (masked), 819 changed (network mostly).
Files: v15/fmap.py, v15/fmap.json (1.0 va -> [1.5 va or null, same|changed]), v15/default_v15.xbe (u5 English).
Plan:
 1. functions15: 1.5 address of every function, changed ones too (boundaries between same neighbours).
 2. data map 1.0 -> 1.5 for globals (xmap.data-style votes from same functions' address fields) - the oracle for 1.5.
 3. pipeline retarget: scripts read H2N_NAT / H2N_XBE / H2N_CSV; workspace /home/claude/native15.
 4. layer: ~150 hard-coded 1.0 addresses (interp.c, xnetx.c, main.c, timing.c, helpers.S, xd3d.cpp...) -> per-version.
 5. build, boot, fix; launcher dropdown; content.
Progress 18 Nov (after build 37): funcs15.py + funcs15b.py -> functions15.json: every 1.0 function's 1.5 address
  (14,974 same; changed: 366 first-of-run by boundaries, 126 by masked prologue, 144 by 1.5 call targets / data code
  pointers; 183 unplaced = never a call target in 1.5, i.e. reached only from changed code, likely inlined in 1.5).
  229 changed functions are called from unchanged compiled code: those need routes with the right convention
  (retailconv-style check on 1.5's code); the other 590 are reached only from changed (retail) code or via pointers.

How the exe is put together (build2.sh)

    and the generated stubs_typed.cpp with the SDK's own CL against its headers (<xtl.h>), so the structures the game
    reads are the SDK's.
  - main, xapi, crt, physmem, timing, dump, retail (.c): see the first item; dump.c writes the stop file, retail.c
    loads retail's code.
  - mkstubs3.py writes a stand-in for every Xbox symbol the layer does not define, in C++ with the prototype the
    SDK's headers declare (all 165 have one), so that it can clear every OUT parameter: logs its first call, clears
    the outputs, returns 0 or the value in stub_returns.json. A stand-in that "succeeds" and leaves its outputs alone
    hands the game stack garbage; that was stage 3's stop.
  - lld-link, image base 0x10000, fixed, large-address-aware; reserve.o FIRST so that 0x11000-0x586000 (where the
    retail image sits on the console) stays free inside our .text. The script prints both ends of that block: they
    must read 0x11000 and 0x586000.
  - At start-up the layer copies .rdata/.data/.data1/$$XTIMAGE/$$XSIMAGE/DSPImage from the user's default.xbe to their
    retail addresses (CRC-checked), applies the initialiser writes, re-aims 9,072 code pointers at our functions and
    makes the retail code range inaccessible.

Rules that must keep holding
  - A layer file compiled with windows.h must not call a Win32 function the layer also defines for the game
    (CreateFileA, CreateThread, VirtualAlloc, fopen ...): the import and the wrapper collide at link. Use the
    h2n_real_* helpers / GetProcAddress, as xapi.c and main.c do.
  - A wrapper that logs must put the last-error value back afterwards (the game reads it after CreateFile).
  - Every call that takes a path must go through h2n_xbox_path: D: is the game folder and is read-only, every other
    drive letter is a folder under .\h2native. The game's remaining direct Windows calls are listed by build2.sh's
    defined.txt against unresolved3.json; none of them takes a path.


Stage 6 additions

The picture (layer2/gfx.h, gfx9.c, xd3d.cpp)
  xd3d.cpp (SDK compiler) keeps the console-side state and hands each draw to gfx9.c (zig cc, <d3d9.h>) through
  gfx.h, in the console's own terms. gfx9.c turns it into Direct3D 9:
  - vertex programs (the 136-slot NV2A program memory, from LoadVertexShaderProgram and from raw GPU commands) ->
    vs_3_0 byte code written directly; the program's screen-space position is taken back to clip space at the end
    (the game supplies its own viewport constants, hardware constants 10 and 11, offset 0.5: hardware coordinates
    have pixel centres at .5, so half a pixel is subtracted for Direct3D 9);
  - register combiners (render states 0-56 + D3DRS_PSTEXTUREMODES; SetPixelShaderProgram copies its definition
    there) -> ps_3_0 byte code; texture modes 0-7, 9, 0xb-0x12 are written, the rest note themselves in the log;
  - textures: unpacked to A8R8G8B8 (swizzled, palettised, 16-bit ...) or passed through as DXT; cached by memory
    address, re-examined once a frame (a sampled hash) and when the game locks them;
  - every surface the game draws into is a render-target texture keyed by its memory, so the game's own texture
    headers that point at the same memory (function_14600 builds such) draw from it; Swap copies the game's back
    buffer surface to the window;
  - the GPU commands the game writes itself (BeginPush/EndPush, the SDK's inline End and visibility test, the
    menu's inline-array quads) are read in order with the calls around them (push_method in xd3d.cpp).
  d3d9.dll and the XInput library are loaded at run time: no new import libraries.
  The SDK's inline SetVertexShaderConstant callers add 96 to the register and pass the count in floats.

The controller (layer2/input.c, xpad.cpp): XGetDeviceChanges/XInputOpen/XInputGetState answered from XInput and the
  keyboard; H2N_KEYS presses buttons at given seconds for tests.

Stage 7: what Windows' Direct3D 9 checks that Wine does not
  CreateVertexShader / CreatePixelShader on Windows validate the byte code and return D3DERR_INVALIDCALL (8876086c);
  Wine accepts anything. Stage 6's vertex shaders all ended with "mad r29.xyz, r12, c192, c193": two different
  constant registers in one instruction. The register tables in Microsoft's reference give "# Read ports" per
  register type (vs_3_0 and ps_3_0: c# 1, v# 1, r# 3): the number of different registers of that type one
  instruction may read. So: one constant register and one input register per instruction, in both shader kinds.
  - gfx9.c now keeps to it: the epilogue is mul + add; the pixel side takes 0, 1, 0.5, 2 from one register (c19)
    and their negatives by the negate modifier; a combiner constant is moved into a register before it is mapped;
    an unused vertex operand reads the zeroed r31 instead of a constant.
  - check_shader() runs on every shader before creation and notes any breach of the rules known so far (read
    ports, written-before-read, one-component operations, declared inputs and samplers, outputs written in full,
    512 instructions). H2N_GFXOLD=1 brings stage 6's epilogue back to show the check catches it.
  - probe_refused() runs when Direct3D 9 refuses a shader the check passed: it tries every instruction alone in a
    small valid shader and logs the ones refused. H2N_GFXPROBE=1 runs it on accepted shaders (to exercise it here).
  - The end of every run logs "picture: N shaders made, R refused by Direct3D 9, F faults found by this build's own
    check". Before a build goes out F must be 0 over a menu tour (H2N_KEYS).
  Under Xvfb, Direct3DCreate9 now and then returns nothing on the first run after a build ("did not start"); run again.


Stage 8: flicker, jointed models, and the first level
=====================================================
The picture
  - xd3d.cpp, D3DDevice_Swap: the console exchanges the memory of its back buffer surfaces at every Swap, and the game
    relies on it: it counts swaps (g_485aa0) and samples g_509354[(count - 1) % 2], its own texture headers over
    back-buffer memory A and B, as "the frame before". Swap now rotates the Data of the back buffer surface objects
    after presenting. Without it every other frame was built on a buffer never drawn into (the flicker).
    Look at consecutive frames, of both parities, before a build goes out: stage 7 was only looked at on even ones.
  - Depth: the game's vertex programs end in screen coordinates with their depth already scaled to the depth
    buffer's range (their constants 10 and 11). gfx9.c takes that range from gx_state.depth_max (16777215, or 65535
    for a 16-bit buffer). Until stage 8 xd3d.cpp wrote a viewport scale and offset into hardware constants 58 and 59
    on every SetViewport / SetRenderTarget and gfx9.c read the depth scale back from there. The game uploads its
    bone matrices to constants 50-106, so every skinned draw got a bone's row as its depth scale and was clipped
    away (the Chief on the profile screens: only the rigid helmet was drawn). Nothing is written into the game's
    constants any more.
  - The address register takes floor(x + 0.001), as the hardware does (the game's own scale, c7.w = 767.8, already
    lands on whole bone numbers; the bias is for programs that scale by exactly 765).
  - Switches for chasing a draw: H2N_GFXCONST=1 (with H2N_GFXFRAME: list the vertex constants each draw is given),
    H2N_GFXDUMP=<program hash> (log the console's program and the shader made from it; scripts/sm3dis.py <file with
    the dumped words> disassembles the shader), H2N_GFXTEST=bits (1 no depth test, 2 no stencil, 4 no culling,
    8 clear black targets to grey: tells "drawn black" from "not drawn").

One name in the source, two things in retail (oracle2.py, rewrite.py, scripts/fieldcmp.py)

  where retail's code has another address and still match. oracle2.py lists such fields ("data fields inconsistent
  with the plan", 85) and now also records every data field of the functions concerned (data_fields in
  oracle2.json). rewrite.py re-aims a reference inside that one function at retail's address when every field of
  the function for the same symbol and offset says the same address, and the function's native object really has
  a reference to that symbol and offset (a private absolute symbol $h2n$at$<address>). 19 references in 6
  functions; it prints one "field:" line per case:
    - function_244980 (the game's ray cast into a cluster): the vtable of its local c_marker_object is retail's
      0x459e0c, not 0x459de4. Retail has two classes here: the shape collection (15 slots, 0x459e0c) and the child
      shape that its slot 13 (0x244bb0, "create") builds into a buffer (10 slots, 0x459de4). The source builds both
      from c_marker_object. With the wrong table, slot 13 was c_244980_base::v3, which takes no arguments: the
      stack came back 8 bytes off and function_3009e0 read its this pointer from the wrong slot (first stop in the
      level, "touching 00000008" at function_3009e0 +0xc0b).
    - g_network_configuration +440 in 0x6fa60 and +504 in 0x90880 (retail reads 64 bytes lower), +376/+380 swapped
      in 0x66330; g_texture_stage_storage halves in 0x1c810 and g_render_source_storage pairs in 0x40e90 (stores
      of the same zero in another order: harmless either way).
  Left alone and printed as "mixed": the same symbol and offset with two retail addresses inside one function

  "no such reference in the function": the field belongs to a neighbouring symbol in our whole-program image (an

Retail code that reaches the console's Direct3D (gen_code.py BACK, retail.c h2n_game_patches)
  A routed function runs retail's code, and that code calls retail's other functions directly. Retail's Direct3D
  is built into the game with conventions of the compiler's own choosing (0x3fdb20 takes edi and esi) and is never
  started here, so retail code must not reach it. Following retail's direct calls from the 16 routes (the calls
  column of functions.csv) reaches 2,190 game functions, and exactly two of them call Direct3D themselves:
    0x1d2f0 (D3DSurface_GetDesc + LockRect; plain stdcall)   and   0x439d0 (D3DDevice_FlushVertexCache; retail takes
    its argument in eax, ours in ecx).
  Retail's copies of both now jump to our build's versions (the second through a two-instruction adapter). The
  stop this cured: a thrown grenade -> object creation (routed 0xb7b40) -> 0xd1e10 -> 0xd30d0 (lighting sample from
  a lightmap) -> 0x1d2f0 -> 0x3fdb20, "touching 00001a14". Redo the search whenever a route is added.
  Not yet handled: retail's 0x21fa80 (unmatched) is reachable the same way and calls six of retail's DirectSound
  internals (0x37b71b ...); nothing has reached it in play so far.
  Handing every matched function back to our build would be the general cure, but only 221 of the reachable ones
  take their arguments as declared (retailconv.py's classify), and retail's callers may also count on registers a
  callee of its own leaves alone, so an adapter would have to save ecx, edx and the SSE registers.

The network (s9t: XNet on the PC's default adapter, layer2/xnet.c)
  The game's network code already calls Windows' own sockets (socket, bind, sendto, recvfrom ... resolve to ws2_32).
  What it also needs from the console's XNet library is in xnet.c: the link status and the title's XNADDR from the
  adapter of the PC's default route (GetBestInterface + GetAdaptersAddresses, loaded at run time, refreshed every 2 s),
  the session keys (XNetCreateKey makes system link keys: the XNKID's flag bits clear), and the console's "secure"
  addresses as the peers' own IPv4 addresses (a table of XNADDR and key per address; a peer not asked about yet gets
  the key registered last). socket() is ours: IPPROTO_VDP (254) becomes UDP with the packets unchanged (the 2-byte
  game data length first). System link opens VDP 1000, UDP 1001 (broadcast), VDP 1005 and 1006 (unknown_092870.cpp).
  XOnline and the QoS calls stay stand-ins (Xbox Live off). H2N_NETWORK=off answers "no network" as before.
