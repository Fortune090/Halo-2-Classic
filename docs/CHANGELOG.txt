H2Classic (stage 9, build s10y) - Halo 2's own code as a Windows program (test build)
=====================================================================================

What this is
  H2Classic.exe is the halo2-decompiled source compiled for Windows. It runs game version 1.0 (the disc's game) or
  game version 1.5 (the game with its last title update, which the map packs need); the Game Version choice in
  H2Classic Settings says which. It takes the game's starting data and the code of the functions the decompilation
  does not have yet (or has only as unproven drafts) from YOUR unmodified default.xbe each time it starts - 1.0 from
  the disc's, 1.5 from the title update's - and reads the maps from the Roms folder; it does not run without them.
  Nothing of the XBE, of the console or of Microsoft is in the exe or written to disk.
  Source code: https://github.com/Fortune090/Halo-2-Classic. H2Classic is free software under the GNU General Public
  License, version 3 or later (LICENSE.txt); LICENSES.txt has its notices and those of the code it uses.

New in s10y (build 47): game version 1.5 - the stop when going into or backing out of a profile's settings
  1. What happened (your two stop files and log, build 46, game version 1.5): leaving Edit Profile - backing out of
     it, or going from it into Appearance - stopped the program with "exception c0000005 at 00235afb".
     - Cause. In 1.5, functions the title update left unchanged run as the compiled source and changed ones run as
       the 1.5 XBE's own code. Which 1.5 function belongs to which 1.0 function comes from a table made by comparing
       the two XBEs. The menus' lists and screens have destructors that are alike byte for byte, or alike but for one
       structure offset, and the comparison had paired two of them wrongly: the destructor of the Edit Profile menu's
       list (1.0's 0x2376c8: its item handler sits 0x388 bytes into the list) was taken for 1.5's 0x237ef9 "with one
       number changed" - but that is another list's destructor (handler at 0x398; it is 1.0's 0x231443). So when the
       Edit Profile screen was closed, the wrong destructor ran on its list and unlinked what lay 16 bytes further on.
       Your stop files show exactly that: the "link" it used is the address of the list's own item routine, and the
       program stopped writing into that routine's code. Whether it stopped depended on one word of memory behind
       the list being non-zero, which is why it came and went. The real 1.5 destructor is at 0x2c146a and is the 1.0
       one instruction for instruction.
     - Since when: the table has had this pairing since 1.5 came in (build 40). It is not from build 46's changes.
     - Fix, in the table's rule (scripts15\map15.py), not for this one case: one 1.5 function is the twin of one 1.0
       function. Where several 1.0 functions had the same 1.5 place, each is now put where the unchanged functions
       that call it say it is, if that place is the function instruction for instruction and everything it calls
       then agrees with the table. 37 pairings moved; 29 functions that were marked "not the same" because of them
       agree now.
     - What that changes in the program: of the 256 functions that compiled code reaches in 1.5's own copy, this was
       the only one sent to another function's twin (checked for all 256). It and eight more now run as the compiled
       source, like the other 17,400 unchanged functions - the eight had only been sent to 1.5's copy because they
       call or name one of the wrongly paired ones: a pause menu and two Xbox Live player-list screen routines, and
       five of the physics set-up routines that run when a map loads. Five tables of 1.5 (virtual function tables)
       that had been paired with the wrong 1.0 table are right now; every slot of each agrees.
       Game version 1.0 is untouched: only 1.5's route list differs (nine entries fewer).
  2. H2Classic Settings: the note under "Generate Xbox keys.bin file" now reads "(used for Xbox save compatibility
     and crossplay with xemu)" - "Xbox/" is out, since system link with a console is not offered. Nothing else in
     that program changed. DLSS Helper.exe is build 46's file.

  Checked here (under Wine, game version 1.5): Settings > Player Profiles > Edit, into Appearance and back, out to
     the profile list and in again - the Edit Profile screen closed several times in two runs: no stop. A Slayer match on
     Warlock (map load, play, pause menu, End Game, Game Over); a System Link lobby created and left; the self test
     (0 of 32 failed).
     Build 46 did not stop here on the same path (one run): here the word behind the list was evidently zero. What
     the fix rests on is your two stop files and the two XBEs' code, as above - not on a stop reproduced here.
  Not checked here: Xbox Live's player-list screens (they need Live), a long 1.5 session.

New in s10x (build 46): system link finds the other players by itself; F11 and F12 are gone; "DLSS Helper.exe"; the source comes with the build
  1. System link with nothing to set.
     - What it does. H2Classic on two or more PCs on the same network: System Link > Available Games lists the
       others' games, and joining works. No address, no port, no adapter, nothing to install (no Npcap), nothing to
       tick: it is how a new h2classic\settings.ini and an old one both behave.
     - Why it could not simply use Windows' network. The game's network code is the XBE's own library, and a console
       addresses its system link packets by network-card address alone: every packet says IP 0.0.0.1 (measured here,
       also when the library was given a router's address). Windows will not send or deliver such a packet; only a
       packet driver can, and none is used.
     - How it works instead. The players' programs carry each other's packets. Each program takes the first free of
       four UDP ports (9369, 9370, 9371, 9368). A packet for everyone ("who has games?", "here is mine") is sent to
       everyone on each network the PC is on, and to the PC itself, on those four ports. From every packet that
       arrives the program remembers which console it came from and where its program is, and a packet for that one
       console then goes straight there. Every three seconds each program says that it is there, so they know of each
       other before anybody opens System Link. Each packet travels as it is, one per datagram - the format of xemu's
       "UDP Tunnel".
     - Windows Firewall. The first start asks whether H2Classic.exe may use the network: allow it (Private networks).
       Without that, two PCs do not hear each other. Programs on one PC reach each other without it.
     - What has to be the same on every PC: the Game Version (a 1.0 game and a 1.5 game do not see each other - two
       consoles would not either), and h2classic\keys.bin - on all of them or on none (it gives the console's system
       link key; without it H2Classic uses its own, and the two kinds do not see each other. The log says which:
       "no certificate key").
     - Two H2Classic programs on one PC work too (each from its own folder), with different console addresses.

  2. xemu. What is possible, and what is not.
     - With xemu's network on its default, NAT: no. I looked for a way and there is none that H2Classic can provide.
       In NAT mode xemu is a small router in front of the console (the library named libslirp): it takes the console's
       packets apart and sends their contents again through Windows, as a program's own connections. A system link
       packet for everyone is a broadcast, and that router's sockets are never given the right to broadcast, so
       Windows refuses it (read in libslirp's source: no SO_BROADCAST anywhere in its UDP code; QEMU's bug 1838228
       reports the same from a user's side). A system link packet for one console is addressed to IP 0.0.0.1, which
       Windows cannot send anywhere. So nothing of system link ever leaves xemu in NAT mode - there is nothing on the
       PC or the network for H2Classic (or any other program, or a packet driver) to pick up, and nothing H2Classic
       sends reaches the console inside. This is xemu's NAT mode itself; it is the same between two xemus.
       Not run here: I did not start xemu in NAT mode to watch it fail; the above is from the source and from the
       0.0.0.1 measurement.
     - With one setting in xemu (no change to xemu itself): yes. In xemu: Settings > Network: Attached to UDP Tunnel,
       Remote Address <the H2Classic PC's address>:9369 - or 127.0.0.1:9369 when both run on one PC - and Bind
       Address left as it is (0.0.0.0:9368). Nothing is set in H2Classic. xemu's tunnel sends everything to that one
       address; the H2Classic there passes it on, so every H2Classic PC on the network sees that xemu and plays with
       it, not only the one it points at. If that H2Classic is closed, the xemu is cut off until it is back.
       xemu needs h2classic\keys.bin on the H2Classic PCs (a console's system link key), as before.
     - A setup that worked with build 45 (xemu's Remote Address 127.0.0.1:9369) keeps working unchanged.
     - A real Xbox: left out, as you decided. It would need a packet driver on the PC.
     - The test launcher keeps the old way under Network: "How players are reached" = tunnel, with the two tunnel
       fields. New there: "This PC only", and the console address.

  3. F11 and F12 do nothing now (F11 wrote two frames into the log, F12 saved a picture of the frame). The window's
     title is "H2Classic". Both keys can be given to game actions in Keyboard + Mouse Settings. The test launcher's key

  4. H2Classic_DLSS.exe is now "DLSS Helper.exe" - the same file under a new name (not rebuilt); H2Classic.exe and

  5. The source: H2Classic_build46_source.zip, laid out like the repository (docs\BUILD.md says where each folder
     goes and how the program is built; docs\DEVLOG.txt has the developer notes of every build since the repository's
     last update). As before it holds no part of the game, the SDK or the console: you bring your own XBEs.

New in s10w (build 45): the sun's glow keeps its shape in widescreen; the picture is always the window's own size
  1. The sun's glow (your picture: the sun stretched at 21:9).
     - Cause. A sky's sun is a lens flare marked "sun". Its rings go through the view like anything in the world, and
       they were round. Its glow is drawn by a function of its own (function_46ea0), and that one works in screen
       pixels: a square of 64 around the sun's point is marked where the sky shows, copied, blurred, and drawn
       sixteen times, each time 5 pixels larger each way - as many pixels across as up and down. In the game's
       widescreen the 640x480 picture is shown wider than it is drawn, so the glow came out as much wider as the
       picture: 4/3 at 16:9 (a console set to widescreen shows it that way too), 16/9 at 21:9, 8/3 at 32:9.
     - Fix, as part of the Widescreen Fix (the HUD is narrowed the same way): every measure across in that function
       is divided by the widescreen factor, about the sun's point - the marked and copied square and the sixteen
       drawn ones. The glow is then as wide on the screen as it is tall. Its height, its brightness and where it is
       are the game's. At 4:3, or with the Widescreen Fix off, the numbers are the game's own, bit for bit.

  2. The picture is the window's size (your two pictures: Window Size 3440x1440 shrunk and 2560x1080 enlarged into
     the same window, with different edges).
     - Cause. The picture was made at Window Size, and each finished frame was then fitted to the window by
       Direct3D: a second resizing whenever the window was not exactly that size - a window Windows made smaller
       because it does not fit the screen, a maximized or dragged window, and every Borderless or Full Screen
       window whose Window Size was not the screen's.
     - Now the picture is always made at the size the window really has, pixel for pixel. The game's drawing
       (640x480 times Render Scale) is resized once, straight onto the pixels shown, and nothing is resized after
       that. Two starts with different Window Sizes that end up as the same window give the same picture.
     - Window Size is the size a WINDOWED window is given. When Windows gives the window another size, or you
       maximize it, restore it or drag its edge, the picture is made for the new size between two frames (black
       for an instant; the log says "the window is now ... inside").
     - Borderless Windowed and Full Screen are the screen: the picture is the screen's size whatever Window Size
       says, and H2Classic Settings greys Window Size out for those two modes.
     - Screens Windows scales (Display settings > Scale at 125 %, 150 % ...): H2Classic now counts in the screen's
       own pixels. Before, on such a screen, Windows enlarged the finished window - one more resizing, and blurred.
       A windowed window is therefore smaller on such a screen than it was for the same Window Size: it now has
       exactly that many of the screen's pixels. (H2N_DPI=0 in the environment puts the old way back, for
       comparing.) At 100 % nothing changes.
     - Render Scale, Aspect Ratio and the black around a picture whose shape is not the window's are as before.

  3. NOT in this build: the vehicles' lights that sit beside the vehicle at a distance (your video on the bridge).
     I have not found the cause yet, and I do not want to guess. What I have so far: an object's light is a lens
     flare, placed on the screen through the same view as the world (function_480a0 / function_48b00), and nothing
     in that path depends on the picture's shape in the code as I read it - so the shift comes from somewhere I
     have not looked yet. One press from you would show it directly: see Test 4.

  Checked here (under Wine):

New in s10v (build 44): the mouse looks, and H2Classic Settings has Keyboard + Mouse Settings
  1. The mouse.
     - In a game, moving the mouse looks around, for the player on port 1. Both game versions.
     - Where it goes in. The game works out a player's look in one function (function_185be0), from the right
       stick. H2Classic adds the mouse's movement to that function's result, the way Halo 2 for Windows Vista does
       inside the same function (read from your copy of its halo2.exe; nothing of that file is in H2Classic):
         . zoomed in, the look slows down by the zoom's magnification, and a stunned unit turns slower, exactly as
           with the stick;
         . in a vehicle seat that has its own turn rates (a turret, a tank's gun) the mouse is slowed in the same
           proportion as the stick is;
         . the turn of what the player stands on is still added;
         . with the stick (or the look keys) pushed at the same time, the larger of the two is the look, for
           left / right and for up / down each;
         . a player who looks with the mouse gets no pull on the view from the aim assist (Vista gives its keyboard
           and mouse player none). Bullets are still drawn to a target and the reticle still turns red, as before.
           Using a controller again brings the pull back.
     - What is this build's own, because the console's game has no mouse: the scale. One count of the mouse turns
       the view 0.022 degrees times Mouse Sensitivity (2.5 from the start: 0.055 degrees a count, a full turn in
       about 21 cm of an 800 DPI mouse), with no acceleration. (Vista puts the mouse through an acceleration curve;
       that is not copied.) The mouse is read as raw input: Windows' pointer speed and "Enhance pointer precision"
       play no part.
     - Look inversion. The game applies its own Look Inversion setting to the stick before that function, so the
       mouse never passes through it: the game's setting does nothing to the mouse. The mouse has its own, Invert
       Look (Mouse Only).
     - The game's Look Sensitivity setting (the stick's turn rate) does not change the mouse on foot either: the
       mouse has Mouse Sensitivity. (Vista scales its mouse by the player's look speed, which there is the mouse's
       own setting; here that part is played by Mouse Sensitivity.)
     - The pointer. While the game is taking the look (in a game, no menu up, the game's window the active one) the
       pointer is hidden and kept inside the window. In the menus, when paused, and when another window is active
       it is free. It is held only for a keyboard and mouse player - once a key, a mouse button or the wheel was the
       last thing used; a player on a controller keeps a free pointer, as before.
     - The mouse's buttons and wheel are keys like any other (see 2). From the start: left button = right trigger
       (fire), right button = left trigger (grenade), middle button = click of the right stick (zoom), wheel
       (either way) = Y (switch weapon). A mouse button counts while the pointer is over the game's picture, and the
       click that brings the game's window to the front does not count.
     - The menus are worked with the keys or the controller as before: the mouse does not point at menu items.

  2. Keyboard + Mouse Settings: a new button in H2Classic Settings, under GAME. It opens a window of its own:
     - Enable Keyboard + Mouse (on from the start, as the keyboard has been). Off: no key is a controller button,
       the mouse does not look, and the pointer is left alone.
     - MOUSE
         Mouse Sensitivity          0.1 to 10.0, 2.5 from the start
         Zoom Sensitivity           0.10 to 2.00, 1.00 from the start. It multiplies the mouse while zoomed in.
                                    1.00 is the game's own rule alone (the look slows down by the magnification:
                                    half as fast at 2x, a fifth at 5x), which is also what Vista does.
         Invert Look (Mouse Only)
     - KEY ASSIGNMENTS: one row for each of the controller's buttons and for each way of its two sticks, named by
       the button and what it does in the default button layout, with two fields each. Click a field, then press
       the new key, a mouse button or turn the wheel; click the field again for the left mouse button; a click
       anywhere else leaves it as it was. Right-click a field (or Delete) to empty it. A key given to one field is
       taken away from any other field that had it. Left and right Shift, Ctrl and Alt are separate keys. Not
       accepted: the Windows keys, Print Screen, and F9, F11 and F12 (H2Classic's own).
     - Reset to Defaults there resets that window only; the settings window's Reset to Defaults leaves the keys and
       the mouse as they are.
     - A running game takes every change at once.

       Anti-Aliasing Off / FXAA / SMAA / TAA, and SMAA's Quality
     Not while it runs: a change to DLSS or away from it. DLSS is started with the game (its own kind of graphics
     device and its helper program), so that change waits for the next start; a note under Quality says so, and the
     game keeps the anti-aliasing it has until then.

  3. How it works.
     The game makes a named mark in Windows when it starts (an event; no file). Settings sees the mark - that is how
     it knows the game is running - and sets it each time it has saved h2classic\settings.ini. The game looks at it
     once a frame, between two frames, reads the file again and does for each changed setting what a start with it
     would have done:
     - Display Mode: the same window gets the other frame and place.
     - Window Size: the graphics device is reset to the new size (the window shows black for one frame).
     - Render Scale: the surfaces the game draws into are let go and made again at the new multiple.
     - Aspect Ratio: the game keeps "widescreen" in one byte, set once from the console's setting when it starts; its
       view, its split-screen layout and the Widescreen Fix read that byte every frame. The byte and the 21:9 / 32:9
       factor are given the new setting.
     - Unlock Performance: the frame pacing's three instructions are re-aimed, or the game's own bytes put back;
       Increased LODs' two places in the game's code are taken or given back; Draw Distance and the in-between frames
       follow. (The rocket launcher's animation fix keeps what it already changed until the game loads that
       animation again.)
     - VSync: the frame clock follows the display, or runs free.
     As before, a setting given in the environment wins over the file. A game started from the test launcher
     (h2classic_launcher.cmd) does not use settings.ini at all: Settings shows GAME RUNNING for it, and its changes
     are for the next start from Settings.

  4. A full-screen game stays on top of every window, so Settings could never be seen over it. While Settings is the
     window in use and the game is full screen, Settings is put on top as well; when the game is clicked (or started

New in s10s (build 41): game version 1.5 - the stop on End Game and Save and Quit, the in-between frames, and the
likely cause of the missing letters and HUD
  All of your reports were about 1.5, and items 1 to 3 are the same kind of mistake of mine: something in the 1.5
  half of the exe that was still 1.0's. 1.0 runs the same compiled game at the same addresses as in build 40.

  1. The stop on End Game and on Save and Quit (your report; your three stop files show the same place).
     Cause: closing the pause menu deletes the menu's screen. In 1.5 that screen's destructor is one of the
        functions the update changed, so 1.5's own code runs for it, reached through a small adapter. An adapter
        has to know how many bytes of arguments its caller expects the function to take off the stack. That
        number was read from the first "ret" instruction of the compiled function. This destructor ends in a
        jump to another function and has no "ret" of its own, so the number came from whichever function follows
        it (4, where it had to be 0). The stack was 4 bytes off after the call, and the next return went to
        address 0.
     Fix: the number now comes from the function's declaration in the source. Three more adapters had the same
        mistake: the destructors of the Live task screen and of the player-selected screen, and one function that
        1.5's code calls. Backing out of the pregame lobby with B stopped the same way here; it is fixed with it.
     Checked here (1.5, Unlock Performance on): after a split screen match on Terminal, Start, End Game, End
        Game gives Game Over, the Postgame Carnage Report and the lobby, and B from the lobby gives Choose
        Profile. After a System Link match I hosted there, End Game gives Game Over as well (I did not wait for
        the report). Start, Leave Game, Leave Game gives the main menu. In the campaign (the opening cutscenes,
        then The Armory), Start, Save and Quit and its confirmation give the main menu.

  2. No in-between frames in 1.5 (your report).
     Cause: the code that draws the frames between two game ticks uses 23 fixed addresses of the game - its
        object, player, camera, effect and particle tables among them - and all 23 were 1.0's. In 1.5 those
        tables are elsewhere; the code's checks on what it read failed, so every frame showed the last tick as
        it was: 30 steps a second at any frame rate.
     Fix: each of the 23 has its 1.5 address. In 1.5 the log has the line "in-between frames: on" again.

  3. Missing or wrong letters, the missing HUD, the corrupt pause menu (your report).
     What your F11 capture shows: the texture the letters are kept in is intact, and so is the list of what is in
        it. One entry of a font's character table is wrong - the capital L of one font points at a 2 x 20 cell at
        an impossible position - so every L in that font is drawn from nothing: "ockout", "SE ECT", "CANCE". So it
        is not a cache that got too full: something wrote over one entry.
     The likely cause is item 2's mistake. One of the 23 addresses belongs to the code that keeps a held zoom
        working at high frame rates, and that code also writes: with Unlock Performance on it read, every frame, a
        pointer from the place where 1.0 keeps its player-control table and could write four small counters through

        what it holds there is the address of a buffer that a file was read into (in your three stop files: four
        different buffers). So the counters went into data that had just come from disk - the letters of a font, a
        texture, a piece of a map - a different piece on each start. That fits letters that differ from reload to

New in s10l (build 34): controller vibration, and Increased LODs really applied
  1. Vibration
  The game works out two motor speeds for each controller (from what happens to you: firing, explosions, damage) and
        hands them to the console every time it reads the controllers. H2Classic took them and threw them away, so no
        build so far has ever made a controller vibrate.
  Now they go to the PC controller in the same port, through Windows' controller library (XInput). The Xbox pad's
        left motor is the heavy, slow one and its right motor the light, fast one; XInput's are the same and use the
        same range (0 to 65535), so the game's numbers go across unchanged. The game's own rules still decide when it
        vibrates: nothing with Vibration off in the player's profile, outside a game or while paused.
  Two things are the PC's, not the game's: the motors stop while another program has the focus (the controller
        reads as untouched then too), and when H2Classic closes (window, EXIT, a crash), so a pad is never left
        running.
  Checked here with a stand-in for Windows' controller library that writes down what it is sent: firing the SMG on

New in s10k (build 33): the light on the ground that disappears when you get close (your video, Ivory Tower)
  The overhead lights' patch of light on the ground is drawn in a pass of its own. Near a light, the game also gives
        that pass the light's shadow map: a depth picture the light "sees". For each pixel of floor the console compares
        that depth with the pixel's distance from the light, and multiplies the light by the result: 1 where nothing
        is in the way, 0 where something is. The game only does this for lights near you; farther away the light is
        drawn without the test.
  H2Classic couldn't read a shadow map (its depth format, 0x2e), so that test read 0 everywhere. "Something is in
        the way everywhere" means the whole patch of light was gone, but only near the light, where the game uses the
        test. Your Metropolis capture from build 28 shows it too: the tunnel light's pass reads its shadow map
        (0x82b1b000, format 0x2e), marked "not available". It has been like this in every build so far: shadow maps were
        on the list of things not read yet since the first builds that drew anything.
  Now the pass reads the shadow map's depth and does the console's compare (the game sets "greater": lit where what
        the light sees is farther away than the floor). So the light on the ground should stay when you walk up to it,
        now with the shadows of whatever stands in it (you, crates, pillars).
  Checked here: every variant of the new shader is accepted by Direct3D 9 (256 shaders made in a test that forced the
        compare onto every texture, none refused, none failing this build's own check), self-test 32 of 32. I didn't
        get to one of these lights here, so how it looks is for you to see.

How to run it
  Put the game in the folder named Rom, next to H2Classic.exe: default.xbe and the maps folder (the v1.0 game
  folder's contents), or an Xbox disc image (.iso) of the game. Then start H2Classic Settings.exe and press Start Game,
  or start H2Classic.exe itself.
  H2Classic.exe "D:\path\to\Halo2"  names another folder (or a disc image) instead of Rom; a second argument can name
      the default.xbe itself.
  A window opens after a second or two. Close the window to stop (or Ctrl+C in the console).

Controls (only while the game's window is the active one)
  A controller that Windows sees as an Xbox controller works as it is (LB = white, RB = black).
  Keyboard:   Enter = Start        Backspace or Esc = Back     arrow keys = D-pad
              Z or Space = A       X = B       C = X       V = Y       1 = white     2 = black
              W A S D = left stick       I J K L = right stick       Q / E = left / right trigger
              F / G = click the left / right stick
  Mouse:      moving it looks (in a game)      left button = right trigger      right button = left trigger
              middle button = click the right stick       wheel = Y
  Every key and mouse button can be changed, the mouse's sensitivity set and the keyboard and mouse switched off
  in H2Classic Settings: Keyboard + Mouse Settings (s10v, above).
  F12 saves a picture of the current frame (h2classic_frame_NNNNN.bmp).
  F9  (only with H2N_INTERP=3) writes the next 4 seconds of a cutscene into the log, frame by frame.
  F11 describes the next two frames in the log, draw by draw, and saves every surface the game drew into during
      them (h2classic_surface_<frame>_<memory>.bmp, a dozen or so files) and the two frames. This is what to press
      when the picture is wrong: it lets me see which draw went wrong without another round. The game crawls for a
      few seconds while it does this.

Profiles from your Xbox
  The game signs each saved file and calls a file "damaged" when the signature does not fit. The console makes that
  signature with a key held in its kernel (one key, the same in every retail Xbox), mixed with a key in the game's
  own XBE. This build does the same calculation, but the kernel's key is not in the exe and I will not put it in a
  file for you: like the XBE, it has to come from you.
    - The launcher's "Generate Xbox keys.bin file" button makes it from your BIOS image and MCPX boot ROM (s10d).
    - Put it in  h2classic\keys.bin  (next to H2Classic.exe, in the folder you start it from). Accepted forms: 16 bytes (the key);
      32 bytes (the keys.bin that Cxbx-Reloaded uses: the EEPROM key, then this key - the second half is used);
      or the same as 32 or 64 hex digits in a text file.  H2N_CERTKEYFILE=<file> names another file;
      H2N_CERTKEY=<32 hex digits> gives it without a file.
    - With the right key your Xbox profiles load here and what this build saves loads on the Xbox. The method is
      checked here against an independent calculation with made-up keys, not against the real one. Your profile
      (the one in U.7z) was tried here by signing it again with the stand-in key: it loads, with every level listed.
    - Without the file the key is all zeros: an Xbox profile shows as damaged (what you saw), and the log's
      "saved files:" line says so.
    - To check a key before trusting it:  $env:H2N_SIGCHECK="path\to\a profile file from the Xbox"  - the log then
      says THE SAME or DIFFERENT for that file's signature. For the profile in your U.7z the signature begins
      a1375f13 f2a0440d and ends 4755.
    - Profiles made by stage 8 and earlier were signed with a stand-in and show as damaged now, with or without
      the key. Make them again, or copy the Xbox ones in.

What it writes, and where (all in the folder you start it from)
  - h2classic_log.txt
  - h2classic_stop.bin, only if the run stops on a fault or hangs. Send it along with the log.
  - h2classic_frame_NNNNN.bmp, only for F12, F11, H2N_SHOT or "shot" in a key file
  - h2classic_surface_*.bmp, only for F11 or H2N_GFXFRAME
  - the folder h2classic: the console's hard disk (map cache, settings, profiles). Stage 8's folder is reused.
    A folder named h2native from an earlier build: rename it to h2classic to keep what is in it.
  - at every start the game empties h2classic\N, as the console formats that drive (its second map cache) at every start
  - H2Classic Settings.exe writes h2classic\settings.ini (and h2classic\keys.bin when you press Generate);
    H2Classic.exe starts H2Classic Settings.exe instead of the game when settings.ini is not there yet
  - with a disc image only: a small file the game opens through the C library is copied out of the image to
    h2classic\D first (the game looks for launch.txt this way; the retail disc has none)
  Nothing else. The game's files in Rom (or the folder you name), and a disc image, are only ever opened for reading;
  keys.bin and the files named by
  H2N_KEYFILE, H2N_CERTKEYFILE and H2N_SIGCHECK are only read.
  To undo everything, delete h2classic, h2classic_log.txt, h2classic_stop.bin and any h2classic_frame_*.bmp and
  h2classic_surface_*.bmp.

What to expect
  - The game draws 640x480 unless H2N_RENDER says otherwise; the window is twice that when the screen is big enough.
  - A level runs at 30 frames a second and the menus at 60: the game's own rates.
  - A skips cutscenes.
  - Shadows that the console draws with a depth texture are left out; lighting of objects in dim places is still
    rough (dark first-person arms).
  - The last lines of the log count the shaders made and how many Direct3D 9 refused (it should say 0). If your
    graphics driver refuses the shaders that write depth, the log says so in a line beginning "picture:" and the
    build falls back to stage 8's depth (no sky). If it has no depth buffer that can be read as a texture, another
    "picture:" line says so and only the fog is wrong.
  - No sound, no videos.
  - See "Still wrong" near the top for what is known and not fixed.

Switches (set before starting; PowerShell: $env:NAME="value")
  H2N_RENDER=1..8   draw at that many times 640x480 (default 1). 2 = 1280x960, 3 = 1920x1440. The HUD and text are
                    drawn at the same multiple, so they get sharper, not smaller.
  H2N_SCALE=1|2|3   size of the window (times 640x480). The same number as H2N_RENDER shows every pixel; a smaller
                    one averages the larger picture down, which smooths the edges (H2N_RENDER=4, H2N_SCALE=2).
  H2N_WIDE=1        the console set to widescreen: a wider view in a 16:9 window (HUD and menus stretched, as there)
  H2N_UNLOCK=1      frames every refresh in a game instead of every second one (see "New in s9d" for what is missing)
  H2N_GFXDEPTH=0    stage 8's depth instead of the console's (for comparing if something looks worse than stage 8)
  H2N_WINDOW=0      no window and no drawing (stops by itself after 3 minutes)
  H2N_SECONDS=n     stop by itself after n seconds
  H2N_SKIPINTRO=1   leave the intro movie out at start (the attract movie and the credits still play)
  H2N_MOVIES=off    no movies at all (as s9r)
  H2N_NETWORK=off   no network, as before s9t (the game is told the cable is out)
  H2N_SHOT=a,b,c    save those frame numbers as pictures;  H2N_SHOT_EVERY=n  every n-th frame
  H2N_KEYS=start@12,a@16   press buttons by themselves at those seconds, or name@f300 at that frame
                    (names: start back up down left right a b x y white black lt rt)
  H2N_KEYFILE=file  read presses from a text file while the game runs: each line added to it is one press (the
                    names above, forward backward strafeleft straferight lookup lookdown lookleft lookright,
                    name*20 to hold it for 20 readings, "shot" to save the frame, "trace" for what F11 does,
                    lthumb rthumb for the stick clicks, "memory" to write h2classic_stop.bin and carry on).
  H2N_WATCH=n       every n ticks, a log line per AI actor and one for the player (place, distance gone)
  H2N_TICK=retail   the game's tick from the XBE's code (experiment; the first-person weapon and body go missing)
  H2N_TABLES=source the 30 table functions new in s9e as the source's drafts again (s9d's behaviour, for comparing)
  H2N_NEWROUTES=off the functions s9f moved to the XBE's code as the source's drafts again (s9e's behaviour)
  H2N_CODEPTRS=retail  the 599 function addresses in the XBE's code left as they are (s9f's behaviour)
  H2N_CERTKEY, H2N_CERTKEYFILE, H2N_SIGCHECK   see "Profiles from your Xbox"
  H2N_INTERP=0      with H2N_UNLOCK: no in-between frames (=2 a line a second about them, =3 a line a frame in a vehicle)
  H2N_HZ=120        with H2N_UNLOCK: this many frames a second instead of the display's refresh rate (a whole part of
                    it - 120, 80, 60 on 240 Hz - is placed on the display's own refreshes). The launcher clears it.
  H2N_LODS=0        with H2N_UNLOCK: the game's own detail levels (no Increased LODs)
  H2N_DRAWDIST=10   with H2N_UNLOCK: the draw distance in tenths of the game's (30 = 300%, the default; 10 = the game's)
  H2N_CARRY=0       with H2N_UNLOCK: lights, particles and effects that moving objects carry stay where the tick put
                    them (for comparing)
  H2N_RENDERONLY=0  with H2N_UNLOCK: the parts only the draw moves (eyes turning to you, some antennas) left to the
                    game's draw (for comparing)
  H2N_AIMLOG=1      a log line ("aim:") for each shot fired near you: where it flew, and how far that is from your view,
                    your aim and the aim of what you ride, in degrees right and up
  H2N_UNROUTE=104150  a weapon's shots fired by the decompilation's draft again (s9q's fix off, for comparing)
  H2N_GFXCACHE=0    every Direct3D 9 setting sent for every draw again (s9r's saving off, for comparing)
  H2N_INTERP=3      with H2N_UNLOCK: F9 in a cutscene writes its next 4 seconds into the log frame by frame
                    The launcher clears the switches above: set them in PowerShell and start H2Classic.exe directly.
  Sound (the other prompt's sound engine, s9p):
  H2N_VOLUME=0.5    the whole mix at that multiple (1 = as the console; 0 to 4)
  H2N_SOUNDWAV=1    also record the mix to h2classic\h2classic_sound.wav (about 11 MB a minute)
  H2N_SOUNDLOG=1    the level of each mix bin and speaker every 5 s, and the first 200 3D sounds' angles and levels
                    (=n for the first n)
  H2N_SURROUND=1    5.1 output (falls back to stereo if the device refuses 6 channels)
  H2N_SOUND=off     play nothing (the sound still runs, on a clock)
  H2N_SOUNDFX=0     the game's effects (reverb, crosstalk) left out: the 3D bins go straight to the speakers
  H2N_HRTF=0        3D sounds without the ear filters;  H2N_HRTF=swap  left and right ears exchanged (for comparing)
  H2N_WMA=off       the music's WMA decoder replaced by silence (if the music ever stops a run)
  H2N_SELFTEST=1    32 checks of the Windows layer instead of the game (start it in an empty folder)
  H2N_DUMP=all      make the snapshot include all of the game's memory (about 55 MB)
  H2N_GFXFRAME, H2N_GFXTRACE, H2N_GFXCONST, H2N_GFXDUMP, H2N_GFXTEST, H2N_GFXHALF, H2N_GFXLAZY, H2N_D3DTRACE,
  H2N_STACK, H2N_BREAK, H2N_POKE, H2N_RETAIL, H2N_ROUTE, H2N_BACK, H2N_UNROUTE, H2N_WATCHLIGHT, H2N_GFXVERTS are for chasing a particular fault: only when asked.
